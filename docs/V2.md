# Croma agentic profit planning and pricing: v2

v2 turns Analysis and Research from single agents that decide everything into harnesses: code owns the stages, the arithmetic and the checks, and language-model workers reason inside them. It also adds an API gateway (see [APIM.md](APIM.md)) and lets a second copy of the system run next to the first. v1 is untouched: it is tagged `v1.0.0` and stays on the `main` branch.

| | v1 | v2 |
|---|---|---|
| Analysis and Research | One agent with tools decides the order, the number of data questions and when it is done | A harness: scope, evidence, conclude, verify, challenge, deliver. The order, the retries and the stopping rules are code |
| Arithmetic | The model computes in its head, or through `calc` | An analytics engine: contribution, rate versus mix, price versus volume versus mix, target gap, concentration, trend, reconcile. Exact, unit-tested |
| Figures in the answer | Trusted | Every figure traced to the evidence ledger; untraceable ones are removed and the reader is told |
| Ratios (margin %, markdown %) | Whatever the agent divided by whatever | The decomposition must be reconciled with the data space's own figure for that ratio, or the plan is refused |
| Hypotheses (Research) | The agent's opinion | Each has a rule over computed figures; code decides supported or ruled out |
| Failure | The run is lost | Every stage saves its output; an interrupted run resumes where it stopped |
| Time for a typical question | Several minutes, variable | Analysis about 1.5 to 2.5 minutes, Research about 2.5 to 5 minutes (measured on the synthetic data; see section 8) |
| Side by side | n/a | `NAME_PREFIX` gives a second, independent set of agents, connections and memory |

## 1. How a run works

```
brief ─► scope ─► evidence ─► [evaluate] ─► conclude ─► verify ─► challenge ─► deliver
        Scoper    code (Data   code         Analyst     code +     Critic       code
        (model)   agent, maths)             (model)     Analyst    (model)
```

`ask_analysis_agent` and `ask_research_agent` keep their names and arguments, so the CX agent is unchanged apart from how it relays the answer. Internally each starts a run in the hub (`hub/harness/`). With `HARNESS_MODE=agent` they fall back to the v1 single-agent behaviour.

**The three workers** are Foundry agents with no tools. Each call is one JSON message `{"task": ..., ...}` and one JSON reply. They run on the deep-reasoning model.

| Worker | Tasks | What it never does |
|---|---|---|
| Scoper (`<prefix>-scoper`) | `analysis_plan`, `research_plan`, `fix_steps` | Query data or write conclusions |
| Analyst (`<prefix>-analyst`) | `analysis_findings`, `research_conclusion` | Compute or recall a number: it quotes the `shown` strings of the evidence and cites the ids they rest on |
| Critic (`<prefix>-critic`) | `review_analysis`, `review_research` | Rewrite: it returns a verdict and precise issues |

**Contracts.** A reply is parsed into a pydantic model (`harness/schemas.py`). If it does not fit, the exact problem goes back once ("step s1 is a rate_mix, so it must be reconciled with ..."). A second failure stops the stage with the reason. Lists a worker over-fills are cut to size instead of failing the reply.

**Stages.**

| Stage | What happens |
|---|---|
| `scope` | The Scoper turns the brief into questions (self-contained, exact dates, units, standing scope, the columns wanted), analytics steps over those columns, a materiality threshold and, for Research, three to five hypotheses with `supports_if` / `refutes_if` rules over the outputs of a step. |
| `gather`, `columns`, `compute` | Questions go to the Data agent in parallel (capped by `DATA_PARALLELISM`). Each answer is mapped to its ledger result by the result id it cites. Columns are matched by code (ignoring case and punctuation; a unique near match is accepted); only a column that is really missing goes back to the Scoper (`fix_steps`). Steps run on the exact rows. Steps that read a result run first, then steps that compare figures (`reconcile`, `materiality`), which may use `s1.current_rate`. |
| `evaluate` (Research) | Each hypothesis rule is evaluated on the figures of its step: supported, not supported, ruled out (refutes rule true) or inconclusive (the step failed, or the rule could not be evaluated). |
| `conclude` | The Analyst gets the evidence pack (what was asked, the filters the data space applied, the figures with their ids and display strings, the top rows of each table, the verdicts). It returns the findings or conclusion, or, in round 1 only, one follow-up request (at most three questions and four steps), which runs through the same gather, columns and compute stages as `gather_2`, `columns_2`, `compute_2`, then `conclude_2`. |
| `verify` | Every number in the text is looked up in the ledger (rounding and unit changes allowed, the same audit the report studio uses) and every cited evidence id must exist. One repair by the Analyst. Whatever is still untraceable is removed (a headline is rebuilt from the engine's figures) and the brief says so. |
| `challenge` | The Critic reviews. A blocking or major issue triggers one revision (`revise`, `verify_2`), and the Critic may ask for the follow-up round if it has not been used. A Critic failure does not fail the run. |
| `deliver` | The brief is rendered by code: headline, driver tables straight from the ledger, ranked drivers or causes, checks that passed, basis, caveats, what was not checked, evidence ids. Findings are saved on the case for the Reporting agent to reuse. |

**Governor.** Workers share one sliding-window token budget (`WORKER_TPM_BUDGET`) and a concurrency cap (`WORKER_PARALLELISM`), so a burst of large calls does not trip the model's rate limit.

**Events.** Each stage emits `stage_start` / `stage_end`; each worker call is an agent call with the harness as its caller. The chat UI shows a Plan / Get data / Compute / Conclude / Verify figures / Challenge / Deliver stepper, the stage on the Analysis or Research node, three dots for the workers, and a collapsible full brief under the answer.

**Resume and export.** `GET /runs/<case>` lists the runs and their stages (`?data=1` adds what each stage saved). `GET /state/<case>` exports the case with its runs and `POST /state` restores both. A restart of the hub empties its memory; if the case was exported first, `POST /state` brings the runs back (one that was executing is marked `failed`), and calling the specialist again with the same brief resumes it at the stage it reached. An unfinished run in a live hub (a failed stage, for example) resumes the same way.

## 2. The analytics engine

`hub/studio/analytics.py` is pure Python with no I/O; `hub/studio/analyze.py` binds it to the evidence ledger (a table `T` and a calculation `D` for every headline figure, so figures are citable and auditable). The same engine is exposed to the report team as the studio tool `analyze` (the Insight agent uses it for decompositions; `analyze` with `op: "help"` lists every operation).

| Operation | Answers | Exactness |
|---|---|---|
| `contribution` | What each segment added to a change in a total | Segment changes sum to the total change |
| `rate_mix` | A ratio (margin %, markdown %, price) moved: how much was each segment's own rate, how much was sales moving between segments | rate effect = w_base × (r_cur − r_base); mix effect = (w_cur − w_base) × (r_cur − R_base). The two sum to R_cur − R_base exactly. New and stopped segments are all mix |
| `price_volume_mix` | A value (NMV) moved: volume, mix or price | volume = (Q_cur − Q_base) × s_base × P_base; mix = (s_cur − s_base) × Q_cur × P_base; price = (P_cur − P_base) × q_cur. Per segment they sum to its change in value, so overall to the total change |
| `target_gap` | Actual against AOP or SOP | Gap, achievement %, concentration of the shortfall |
| `concentration` | How much sits in the top few | Shares, cumulative share, segments needed for 80 percent, HHI |
| `trend` | Direction and size over time | Period changes, least-squares slope, peak, trough, volatility |
| `reconcile` | Two figures that should agree | Difference, difference %, within tolerance |
| `materiality` | Is a change big enough against its base | Relative and absolute floor |

Segment tables carry a `material` flag (a segment must carry `min_share` of the gross movement and clear an absolute floor). Rows labelled like a total are set aside as a control total and checked against the sum. The tests include 40 random decompositions that must add up exactly, with zeros, new and stopped segments.

## 3. Guardrails, and why they exist

Each of these came from a live run, not from speculation.

| Guardrail | Why |
|---|---|
| A `rate_mix` step must be reconciled with the data space's own figure for the ratio (the plan is refused with the fix in the message) | The first live run divided profit from the cost table by NMV from the sales table. The ratio (10.34%) was not the margin Croma reports (10.88%). The harness now asks the data space for the ratio itself and ties the decomposition to it. A mismatch is shown to the reader and the Analyst. |
| Every question ends with the standing scope sentence and states the unit | Genie's SQL varies between runs: one run omitted the merchandise-article filter, another returned NMV in rupees under a "₹ Cr" label. `data_profile.json` holds `standing_scope`; the Data agent checks the SQL applies it. |
| The WHERE filters of each result are in the evidence pack, and the Critic compares them | Different questions in one run must be on one basis. |
| Figures are written by code (`shown`) with units and signs; the Analyst quotes them | Models mangle units and signs. |
| Reconcile against figures the user quoted in the brief | Shows whether the data space reproduces what the user sees. |
| Untraceable figures are removed, not shown | A wrong figure is worse than a missing sentence. |
| One bounded follow-up round | Drill-downs (which class inside the top category) are valuable, but an open loop is how v1 runs wandered. |

## 4. Configuration

Hub settings (environment variables on the container app; defaults in `hub/settings.py`):

| Variable | Default | Meaning |
|---|---|---|
| `HARNESS_MODE` | `harness` | `agent` falls back to the v1 single agents |
| `NAME_PREFIX` | `croma` | Prefix of every agent name; must match the agent deployment and the chat UI |
| `ANALYSIS_MAX_QUESTIONS` / `RESEARCH_MAX_QUESTIONS` | 6 / 8 | Data questions in the first round |
| `ANALYSIS_CRITIC` | `on` | Research always has a critic; Analysis can run without one |
| `WORKER_TPM_BUDGET` | 150000 | Tokens per minute the workers may use on their deployment; keep it under the quota |
| `WORKER_PARALLELISM` | 2 | Worker calls in flight at once, across all runs |
| `WORKER_TIMEOUT_S` | 900 | One worker call |
| `DATA_PARALLELISM` | 4 | Data questions in flight (protects the SQL warehouse) |

Agent deployment (read from the shell by `python -m agents.deploy_agents`): `WORKER_MODEL`, `WORKER_MODEL_<ROLE>`, `WORKER_EFFORT_<ROLE>` (scoper medium, analyst and critic high), plus the existing `REPORT_MODEL*` and `AGENT_MODEL`.

Data profile (`config/data_profile.json`): add `standing_scope` (one sentence) and, in `facts`, how each ratio is defined (which table and rows give the numerator and the denominator). The Scoper, Analyst, Critic and Data agent are all rendered from it.

## 5. Running v1 and v2 side by side

Everything v2 creates has its own name, so the live v1 system is not touched:

1. In `infra/config.ps1` set `App = "croma-tools-hub-v2"` and `NamePrefix = "croma2"`.
2. `infra\deploy_hub.ps1` deploys the hub and creates the connections `croma2-hub-genie|agents|context|studio`.
3. Give the new hub identity access to Databricks (a new container app has a new managed identity): `python integrations/genie/grant_hub_access.py --host ... --warehouse-id ... --space-id ... --catalog ... --hub-app croma-tools-hub-v2 --resource-group ...`.
4. `$env:NAME_PREFIX = "croma2"; python -m agents.deploy_agents` creates `croma2-cx`, `croma2-data`, `croma2-scoper` ... and the memory store `croma2-user-memory`.
5. Run the chat UI with the same `NAME_PREFIX`: `uvicorn ui.backend.main:app --port 8001`.

To go back, point users at the v1 URL and agents; v1 has no dependency on anything v2 created.

## 6. Operating it

* Run a harness without the CX agent, with timing per stage: `python tests/harness_call.py analysis "<brief>" --out brief.md` (or `research`). It follows the run through `/runs/<case>`, so a dropped connection does not lose it.
* See what a run did: `GET /runs/<case>?data=1` (the plan, the answers, the computed figures, the findings, the critique).
* Redeploy: export `GET /state/<case>` for cases you want to keep, redeploy, `POST /state` (this restores the ledger, the case and its runs). The rendered report files are not part of the export: call the studio tool `render_report` on the restored case to publish them again (the report gets the next number).
* A run that failed (a worker returned something unusable twice, the data agent timed out) can be resumed by calling the specialist again with the same brief: it restarts at the failed stage and keeps everything before it.

## 7. Tests

`python -m pytest tests -q` (no Azure access needed): the analytics against hand-computed numbers and random exactness checks, the harnesses end to end with scripted workers and a stub Data agent that registers real ledger results (every stage, repair, removal of untraceable figures, follow-up rounds, column mapping, resume, no-data failure, a failing critic, failing reconciles), the schemas and their error messages, the governor, the name prefix, and that every JSON example in the worker prompts is accepted by the schema that will parse the reply.

## 8. What the live tests showed

Measured on the synthetic Croma data in the test subscription. Stage timings are from `/runs`.

| Run | Result | Time |
|---|---|---|
| Analysis: why did Stores margin % move, Aug to Sep 2026 | 10.88% to 11.92% (+1.04 pp): rate +1.11 pp, mix −0.07 pp; top categories iPhones +0.35 pp, Laptops +0.19 pp. Matches the independent calculation from the raw rows and the earlier verified figures. Reconciles passed | 94 to 117 s |
| Analysis: how did Stores NMV move, what drove it | −₹16.56 Cr (−13.9%): volume −16.10, mix −1.68, price +1.22 | about 2 min |
| Research: why did Stores margin rise | Five hypotheses evaluated by rule; the rise is the categories' own margin rates, not mix; reconciled to the data space's figure and to the user's quoted figures | 2.5 to 4.7 min |
| Through the CX agent and the chat UI | Same figures, relayed in plain language with the full brief one click away | 157 s |
| Full standard weekly report through the CX agent (5 to 11 Oct 2026 against the aligned week of 2025) | Published: 15 pages, 7 sections, 52 evidence items, **122 of 122 figures traced**. The Insight agent used the new `analyze` tool (price, volume and mix; target gaps). The reviewer sent the first draft back with three blockers (a full-scope plan compared with merchandise-only sales; an NLC cost join); the second review scored 4, 4, 4, 3, 4 of 5 | about 60 min |

Problems found and fixed on the way: the margin-basis mismatch above; Genie omitting a standing filter; amounts returned in rupees under a crore label; figures printed as "₹-16.56 Cr"; a long Azure CLI token call timing out on a busy laptop (the credential now waits up to 90 s); `az acr build` occasionally hanging after the build succeeded (update the app with the built image tag instead).

Seen in the report run and not fixed here:

* **Two agent runs ended on the model's token rate limit** (the Insight agent, then a Writer; each gave up after five 65-second waits and the Reporting agent started them again, which worked). About 23 of the 60 minutes were lost this way. Measured use was far below the deployment's 500K tokens per minute (about 1.25 million input tokens over the hour, never above about 55K a minute averaged over five minutes) and Azure Monitor showed no throttled requests, so this looks like a service-side throttle on bursts of reasoning calls and not sustained demand. If it recurs at Croma, ask for more quota or give the report team its own model deployment (`REPORT_MODEL`) so the harness workers and the report team do not share one. The bridge now tells the calling agent that this failure is transient ("ask again in a minute") and not "try a smaller question".
* **The chat turn ended at about 38 minutes** with "the report is still being prepared", although the CX prompt says to keep waiting; the Reporting run was still going and published about 20 minutes later. The hub's own wait for the Reporting agent (`AGENT_CALL_TIMEOUT_S`, 3,600 s) also ran out, which does not stop the run. A report that outlasts a chat turn needs a completion notice (a Teams message or a nudge), which is not built.

## 9. Known limits and next steps

* **Genie's SQL is not deterministic.** The harness detects basis differences (reconciles, filters in front of the Critic) but cannot make the data space deterministic. The durable fix is on the Databricks side: certified measures and trusted assets for the metrics that matter, and a golden-question regression set. That is the Evaluations workstream, deliberately not started here.
* **Reporting is still the v1 editor.** Its stage order is chosen by a model, which is why a full report takes 35 to 60 minutes and is fragile at the writer stage. The runtime is ready for it: the report becomes a third spec of the same pipeline (plan, evidence, insight, actions, one writer per section in a fixed order, review, render). The `analyze` tool is already available to the Insight agent.
* **State is in memory.** Runs, cases and the ledger survive a redeploy only through `/state` export and import. A durable store (Blob or Cosmos) behind the same interface is the next step.
* **One follow-up round.** A deeper drill-down is a new question to the CX agent, which reuses the case.
* **Memory shapes what the CX asks.** The CX agent remembers how a user defines terms such as "category drivers" and then restates the interpretation ("Agreed interpretation: ...") and goes ahead without asking again. That is the intent, but the agents are deployed with one shared memory scope by default, so in a pilot with several people one person's preferences apply to everyone. Deploy the agents with `MEMORY_TOOL_SCOPE='{{$userId}}'` behind the gateway to give each user their own (see [APIM.md](APIM.md)).
* **The progress view behind the gateway.** The hub's event log is global, so with sign-in on the live agent network and the stage stepper are empty unless `deploy_apim.ps1 -ShareHubEvents` is set, which is only sensible for a pilot with one or a few testers. Filtering the feed per user, by the cases their own turns created, is the proper fix and is not built.
* **Rounding.** A decomposition built from rounded category rows can differ from the data space's own total by 0.01 pp (10.87% against 10.88% in one run); the brief says so under caveats.
* **Cost.** An analysis is about three worker calls and a research about four to six, plus the Data agent's calls; the governor keeps bursts under the quota but the quota is shared with every other agent on the deployment. A full report used about 1.25 million input and 113 thousand output tokens.
